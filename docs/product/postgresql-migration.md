# PostgreSQL migration and compatibility strategy (LibrePeople)

State as of this work: integration branch HEAD `68d384a` on `feature/librepeople-production`;
team read-only audits on Karmathy/main at `c9ced0f`.

## 1. Objective and decisions (as of this work)

- **Target database: PostgreSQL.** New installs of LibrePeople run on PostgreSQL; it is the preferred database going forward.
- **Existing Oracle installations: Oracle Autonomous DB stays.** Nothing forces an existing customer off Oracle; the Oracle chain is preserved and continues to work.
- **New installs: PostgreSQL.** The self-hosted installer creates the new database directly as PostgreSQL; no Oracle→PG cutover is required for new customers.
- **Migration window: none required.** There is no forced Oracle→PG cutover now, so no dual-database window is planned.
- **Legal entities (PRD A: multiple legal entities per customer, LibrePeople_DOC 04): PostgreSQL native schema.** One table per legal entity relationship with plain columns; no extension.

## 2. Inventory

- **ORM models:** 26 model files in `backend/app/models/*.py` (excluding `__init__.py`); ~100 model classes; SQLAlchemy 2.0 + Alembic; chain head = `0034_pg_foundations` (35 revision files `0001_baseline`…`0034_pg_foundations` via `0033_login_failure_window` + `lp_files_url_rewrite`; note: the team audit counts 14 revisions on Karmathy/main at `c9ced0f` — the integration-branch state differs).
- **Oracle-specific features found in the current tree:**
  - `Identity()` in 26 files — `backend/app/models/user.py:19`, `backend/app/models/refresh_token.py:63` (plus the other 24 files).
  - Text-CLOB usage: `backend/app/core/schema_drift.py` (only CLOB hit in `backend/app`).
  - `Numeric(12, 2)` usage: `backend/app/models/offboarding.py:29`, `backend/app/models/payroll.py` (71, 170, 171, 172, 188, 189), `backend/app/models/recruiting.py:67`, `backend/app/models/performance.py` (85, 86, 87, 117, 118).
  - Oracle `DEFAULT SYSDATE`: not found in the current `backend/` tree (grep). The audit flags it for the Oracle chain on Karmathy/main — confirm against that state before any Oracle deprecation.
- **Tests:** current tree has 2 test files — `backend/app/rules/test_determinism.py` (15 tests) and `backend/app/rules/test_reconciliation.py` (8 tests) — plus `scripts/test_adb_connection.py`. The audit counts 22 tests compiling against SQLite/Oracle; the PG run must cover the same set.
- **PG equivalents:** `Identity()` → `GENERATED BY DEFAULT AS IDENTITY`; `CLOB` → `TEXT`; `Numeric(12, 2)` → `NUMERIC(14, 2)`; Oracle `SYSDATE` defaults → `CURRENT_TIMESTAMP`.

## 3. Strategy

**Option A (chosen): head PG baseline + dialect-aware env.py.**

The PG chain = the existing head baseline (`0032_india_aadhaar_encryption`) with the full schema rendered for PostgreSQL, plus dialect-aware `backend/migrations/env.py:81` (`_database_url()`; runtime engine/dialect selection) so the same head revision renders PG DDL on PG and the Oracle chain is untouched on Oracle.

- **Work:** one new PG baseline migration (auto-generated from the PG-dialect model metadata, or from an Oracle schema dump + translation) + env.py dialect wiring.
- **Data risk:** minimal. Existing Oracle installs keep the Oracle chain; new installs start on empty PG.
- **Existing-Oracle-install handling:** Oracle chain preserved end-to-end; no schema changes on the Oracle path during this phase.

**Option B (rejected): port all 33 revisions to PG.**

- **Work:** high — a full parallel port of every revision.
- **Data risk:** breaks Oracle history and risks live customer data if any Oracle install is forced to switch.
- **Existing-Oracle-install handling:** no — Option B requires the both-branches shape anyway.

**Option C ("both branches") — the shape of what is chosen, minimally:**

Full Option C = two independent chains (Oracle `0001`–`0032` + PG chain), each with its own head, selected per database. Chosen Option A = the minimal both-branches form: Oracle chain untouched + PG head baseline. Full C stays the shape if the PG chain later needs to diverge from the head.

**Owner decisions (their decision, not the model's):**

- (a) Current database of any live customers (Oracle or PG?) — product owner.
- (b) Data-migration window for the Oracle→PG transition — product owner.
- (c) Timeline (when existing customers move to PG; when Oracle deprecation starts) — product owner.
- (d) Whether to deprecate Oracle on the first PG cutover — product owner; if yes, open a code-cleanup ticket.

## 4. Open decisions (no decision made)

- (a) Data snapshot and cutover for customers on Oracle — deferred.
- (b) Zero-downtime migration tooling — deferred.
- (c) Code-level GLB migration of existing revisions in place vs. a fresh PG chain — decided for now: fresh PG head baseline (Option A); in-place GLB porting of the Oracle chain is future work.

## 5. Verification gate

1. **Fresh install on PostgreSQL 19 (manual, clean environment)** — clean install; assert all PG revisions apply and models create cleanly.
2. **Clean install on Oracle 19.4** — assert the Oracle chain still applies unchanged (no env.py regressions).
3. **PG migration from Oracle export/import** — dump Oracle, import/restore into PG 19, run the PG chain, diff schema vs. target.
4. **Backup & restore tested for both databases.**
5. **PostgreSQL schema drift check** — schema-diff the baseline vs. model metadata (e.g., `alembic check` / drift tooling) to prove the baseline is complete.

Who runs what:

- **Builder** — writes the PG baseline migration + env.py wiring; runs the manual clean installs on PG 19 (and Oracle 19.4 where feasible).
- **CI** — automates: clean install on PG 19, Oracle 19.4 clean install, backup/restore, schema drift check.
- **One human** — sign-off: PG 19.4 clean install green, Oracle 19.4 green, drift check green, export/import round-trip green.

## 6. Stage 3 — DB foundations (done, this change)

Foundations for PostgreSQL without touching the Oracle chain:

- **Migration:** `0034_pg_foundations` chained on `lp_files_url_rewrite`
  (single head). PostgreSQL-only `CREATE EXTENSION IF NOT EXISTS
  "pgcrypto"`; no-op on Oracle/SQLite. Downgrade is a deliberate no-op.
- **Compose:** `db` service (`postgres:16-alpine`), `pgdata` volume,
  `pg_isready` healthcheck; `backend` `depends_on: db (service_healthy)`.
  `DATABASE_URL` still selects the database, so Oracle installs are unaffected.
- **Container probe:** `backend/Dockerfile` `HEALTHCHECK` against the public
  `/health` (python urllib; the slim image ships no curl). Authenticated
  `/health/*` probes unchanged.
- **Env:** `.env.example` Option C block (`POSTGRES_*` placeholders +
  commented `DATABASE_URL` for localhost and compose `db` host). No secrets.
- **Ops:** `scripts/db_backup.sh` / `scripts/db_restore.sh` (custom-format
  `pg_dump`/`pg_restore --clean`, libpq env, confirmation gate) plus
  `docs/runbooks/db-backup-restore.md`.
- **Verification (this machine):** `alembic heads` → single head
  `0034_pg_foundations`; `alembic history` linear; `alembic upgrade
  head --sql` renders offline; compose file validates as YAML
  (docker engine not installed here, so `docker compose config` was not run).
