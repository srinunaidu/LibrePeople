**One row per capability**, keyed by the ID in `docs/product/FEATURE_CATALOG.md`.


## Status vocabulary

| Status | Meaning | The test |
|---|---|---|
| `implemented` | The behaviour exists and an automated check or journey demonstrates it. | The evidence names a green check at a named commit. |
| `partial` | Some of the behaviour exists, or it exists without a required property. | The evidence names what is missing. |
| `missing` | Not built. | No endpoint, model or screen serves it. |
| `broken` | It exists and it does the wrong thing, or it fails open. | The evidence names the defect. **A broken capability is worse than a missing one.** |
| `in-flight` | Built in an unmerged branch or working tree, not yet merged and not yet gated. | The branch or path is named. |
| `blocked` | Needs a decision, a credential, a verifier or an approval. | The blocking item is named. |
| `not verified` | Evidence unavailable or a test could not be completed. | Stated as such, with why. |

**The evidence rule** (adopted from `agents/qa-validation/DECISIONS.md` DEC-012): a capability is `implemented` only when an automated check at a named commit demonstrates it. Reading the code is not evidence, and neither is a live response on its own.
